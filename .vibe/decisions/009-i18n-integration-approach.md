# Localization (i18n) integration approach

**Context:** Backlog item 009 adopts the shared `web-ui-kit` i18next integration layer (`initI18n`, `t`, `<wuik-locale-switcher>`, roadmap decision `023`) so this app's UI strings move into `src/i18n/en.json`/`fr.json` and the user can switch language live, without a page reload, with the choice persisted across reloads. The sibling `lifebar-viewer-web` repo already adopted the same shared layer (its own `.vibe/decisions/007`); this app's approach is ported from it and adapted to a heavier, more stateful editor UI (file-load status, an already-expanded elements editor, a mid-flow save/export warning, an already-decoded sprite browser).

**Decision:**
- The app's brand name ("Lifebar Editor") is left untranslated, treated as a proper noun — same as `lifebar-viewer-web` — only descriptive text, status/error messages, and accessible labels move into the catalogs.
- A thin wrapper (`src/i18n/i18n.ts`) mirrors `web-ui-kit`'s own `t(key, defaultValue, vars?)` contract exactly, under this app's own namespace (`"lifebar-editor"`) and its own `localStorage` key (`"lifebar-editor-locale"`, not the shared default — every OpenKakutou app deploys on the same GitHub Pages origin, so sharing the default key would leak one app's language choice into every other one). Every call site's `defaultValue` is kept identical, character for character, to the English catalog entry for that key, so a render produces the same text whether or not `initAppI18n` has resolved yet — the existing test suite keeps asserting plain English text unchanged.
- `initAppI18n` is only ever called from the real bootstrap (`mount()` in `main.ts`), awaited before the first `renderApp` call — never from `renderApp` itself, which stays synchronous so tests can keep calling it directly.
- Live locale-switching is split by how much state a re-render would otherwise destroy:
  - The elements editor and the New Lifebar Wizard hold no locale-sensitive state a full re-render would lose (the elements editor's expanded-sections `Set` is already threaded through and preserved by the existing `refreshElementsEditor` closure) — `main.ts`'s own `onLocaleChange` subscription just re-invokes their existing render calls.
  - The Undo/Redo and Save/Export buttons' shortcut-hint `title`/`aria-keyshortcuts` are recomputed directly by `main.ts` (the only place that knows both the translated base label and the shortcut manager's live binding) rather than re-running `bindShortcutLabel`, which would attach a second `"change"` listener on the shared manager on every language switch.
  - The lifebar file input, the sprite sheet input, the sprite browser, and Save/Export's own status text each hold session-important state a full re-render would destroy or reset (an already-loaded file's status, an already-decoded sprite sheet's thumbnails, a pending "Export anyway" warning) — each subscribes to `onLocaleChange` once, internally, from a small stored status descriptor (a tagged kind plus its raw parameters, mirroring `lifebar-viewer-web`'s own `MainStatus`/`SpriteStatus`) rather than a pre-formatted string, re-formatting only its own already-shown text in place.
  - The Keyboard Shortcuts section's collapsed/expanded state is preserved the same way (an internal subscription re-translating only its own header label), since a caller-driven full re-render would reset it to its own default (expanded).
- Pluralized fragments ("1 group" vs "3 groups") are avoided by phrasing every count with a parenthesized number (`"Elements ({{count}})"`, `"Sprites ({{count}})"`) rather than a pluralized noun — this app's existing English text already uses that shape everywhere, so no plural-rule handling (i18next's or a hand-rolled one) is needed at all.

**Reason:** These choices keep the existing, already-large test suite passing with minimal, surgical edits, and specifically avoid two concrete regressions a naive "re-render everything on locale change" implementation would introduce in this app: losing an already-loaded file's status/an already-decoded sprite sheet's thumbnails (forcing the user to redo real I/O and a real WASM decode), and accumulating a duplicate shortcut-manager `"change"` listener per language switch over a long session.

**Rejected alternatives:**
- *Every view subscribes to `onLocaleChange` uniformly, including stateless ones* — rejected: the elements editor and wizard are already fully re-rendered on other triggers (a new sprite sheet, a new document) via `main.ts`-owned closures; adding a second, redundant subscription inside them would just be more code for the same outcome.
- *`main.ts` re-invokes every section's render function wholesale on a locale change, including the file inputs and sprite browser* — rejected: these are the exact components whose internal state (loaded/decoded/mid-warning) must not be reset by a language switch, which a wholesale re-render can't tell apart from a first mount.
- *Sharing `web-ui-kit`'s default `wuik-locale` storage key* — rejected for the same cross-app-origin-collision reason `lifebar-viewer-web`'s own decision 007 already documents.
