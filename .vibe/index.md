## Modules
- [`modules/app.md`](modules/app.md) — application entry point, mounts the `web-ui-kit` app shell plus the lifebar file input and the sprite sheet input into the DOM
- [`modules/lifebar.md`](modules/lifebar.md) — the lifebar `.def`-style format itself: a generic, unevaluated data model and its text parser
- [`modules/wasm.md`](modules/wasm.md) — bridge to the sibling `sff` library's WebAssembly build: loads a sprite sheet's metadata and batch-decodes sprite pixels, distinguishing a WASM-startup failure from a WASM-reported parse error
- [`modules/input.md`](modules/input.md) — two single-file inputs (lifebar, sprite sheet): read, parse/load, and report a typed result; render the picker + drag-and-drop UI
- [`modules/viewer.md`](modules/viewer.md) — the sprite sheet browser: a collapsible group list, each expanded group's sprites batch-decoded into thumbnails at once
- [`modules/document.md`](modules/document.md) — in-memory representation of the currently loaded lifebar file and sprite sheet, for later editor screens to read from
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts, e.g. downloading the `sff` WASM release build

## Observed patterns
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`, using Vitest + jsdom
- Whether `web-ui-kit`'s design tokens stylesheet actually loaded is detected by probing a known `--wuik-*` custom property via `getComputedStyle`, not a stylesheet load/error event — a failed load degrades to a plain, dependency-free error state instead of a broken or blank shell
- A format this app doesn't fully interpret yet is modeled as ordered lists of raw, unevaluated key/value data rather than typed fields per known key — mirrors the sibling `character` Go library's own `.cns`/`.cmd` controller philosophy, and is what makes an unrecognized (e.g. Ikemen-only) section/key round-trip through unchanged for free
- Sections/entries in a format that can legitimately repeat a name/key are stored as ordered arrays, never a `Record`/`Map`, which would silently drop a duplicate
- File bytes/text are read via `FileReader` (`readAsText` for the lifebar input, `readAsArrayBuffer` for the sprite sheet input and every sibling app's own binary-format input) rather than the `Blob` read methods, since the project's pinned jsdom version has an incomplete `Blob` implementation — the same real-browser/jsdom parity concern recurs across every OpenKakutou editor/viewer app
- The DOM-building logic of a screen/component is a pure exported function (`renderApp(root, version, options?)`, `renderLifebarFileInput(root, options)`, `renderSpriteSheetInput(root, options)`, `renderSpriteBrowser(root, spriteGroups, sffBytes, options?)`) taking its target element and data/callbacks as parameters, kept separate from the module-level bootstrap — same "inject external effects for testability" shape applied to DOM construction
- Module-level, in-process application state with no external effect to substitute in tests (`lifebar-document-store.ts`, `sff-sprite-sheet-store.ts`) is a plain get/set pair with a test-only reset function, mirroring `character-editor`'s own `character-document.ts`
- A single-file input is a wholesale-replace state machine (idle/loading/success/error, new drop discards the previous outcome), distinct from a multi-file accumulating input (`character-editor`'s own file input) — the two are deliberately different interaction models for different-shaped problems, not a missed convention; both of this app's own file inputs (lifebar, sprite sheet) follow it
- A WASM bridge (`wasm/bridge.ts`) loads `wasm_exec.js` via injectable fetch + `new Function(source)()` (works identically in a real browser and jsdom/Node) and calls `go.run(instance)` without awaiting it (the Go runtime's `main()` never returns), memoizing instantiation across calls — ported field-for-field from `character-viewer-web`'s own bridge to a different WASM module, same rationale (`.vibe/decisions/002-wasm-bridge-loading-and-result-shape.md` in that repo)
- A WASM bridge call returns a typed `{ok, ...} | {ok: false, error}` result for a *module-reported* error, but *rejects* (doesn't catch) if bringing the module itself up fails (fetch/instantiate) — callers needing to tell "the module wouldn't start" apart from "the module ran and reported a bad file" (this app's `sprite-sheet-input.ts` does, for its setup-error vs. parse-error distinction) wrap the call in their own try/catch rather than the bridge doing it for them
- A WASM-dependent module's tests run against the real downloaded build (`public/wasm/`, fetched via `npm run wasm:download`) plus a small real fixture file copied into the app's own `testdata/`, not a mocked WASM module — same convention `character-viewer-web` established for its own bridge tests
- A UI needing to decode several related items at once uses the WASM bridge's own batching support (one call, many `[group, image]` pairs, `sffBytes` transferred once) rather than one call per item — `sprite-browser.ts`'s per-group thumbnail decode (`.vibe/decisions/003-sprite-browser-batches-thumbnails-per-group.md`)
- A collapsible section that lazily creates its own child DOM on first expand (rather than upfront) gates any one-time async kickoff (a decode call) behind the exact same `mounted` guard used for the DOM creation itself — collapsing and re-expanding never re-fires the effect or re-flashes a loading state, since nothing about re-expanding touches that guard
